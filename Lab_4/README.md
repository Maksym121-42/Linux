## Завдання 4.1
Максимальний обсяг пам’яті, який може бути виділений одним викликом malloc(3), визначається не лише типом size_t, а також обмеженнями реалізації та архітектури.
Для x86_64 формальна межа типу size_t становить 2^64−1 байт, однак у практичній реалізації malloc використовується обмеження PTRDIFF_MAX = 2^63−1 байт, тому теоретична верхня межа одного виділення становить приблизно вісім ексбібайтів, а не шістнадцять ексбібайтів.
Для x86 (32-біт) максимальний аргумент malloc дорівнює 2^32−1 байт (близько чотирьох гібібайтів), хоча фактично доступний обсяг менший через обмеження адресного простору процесу та операційної системи.

## Завдання 4.2 

При запуску на 32-бітній системі:  
`neg = -100, p1 = (nil)`  
`num = -1794967296, p2 = (nil)`

При запуску на 64-бітній системі:  
`neg = -100, p1 = (nil)`  
`num = -1794967296, p2 = (nil)`

Опис результату:  
В обох випадках `malloc` повернув `NULL` (`(nil)`). Це означає, що пам’ять не була виділена: для від’ємного значення `neg` і для значення `num`, отриманого після переповнення signed `int`.

## Завдання 4.3

При запуску програми отримано результат:  
`malloc(0) returned non-NULL pointer: 0x5863add2f2a0`

Пояснення:  
Виклик `malloc(0)` має спеціальну поведінку: реалізація може повернути або `NULL`, або ненульовий вказівник. Обидва варіанти є допустимими. У цьому випадку повернувся ненульовий вказівник. Його дозволено передавати у `free()`, тому програма завершується коректно.

## Завдання 4.4

У наведеному фрагменті коду є помилка керування пам’яттю. Після виклику `free(ptr)` вказівник `ptr` не обнуляється, тому на наступних ітераціях циклу перевірка `if (!ptr)` вже не виконується, хоча пам’ять уже звільнена. У результаті програма може повторно використовувати вже звільнену ділянку пам’яті та повторно викликати `free` для того самого вказівника, що є некоректною поведінкою.

Тестовий випадок було реалізовано у двох варіантах:
1. `bad_demo` — після `free(ptr)` вказівник не змінюється;
2. `good_demo` — після `free(ptr)` виконується `ptr = NULL`.

Результат:
- у неправильному варіанті присутній ризик помилок типу використання звільненої пам’яті та подвійного звільнення;
- у правильному варіанті (`ptr = NULL` після `free`) повторні ітерації працюють коректно, оскільки пам’ять за потреби виділяється заново.


## Завдання 4.5

Під час виконання `realloc` було зроблено спробу виділити дуже великий обсяг пам’яті.  
Результат запуску:

`До realloc: ptr=0x61cb7e6dc2a0, дані=ok`  
`realloc не зміг виділити пам’ять: tmp=NULL, errno=12`  
`Старий вказівник досі валідний: ptr=0x61cb7e6dc2a0, дані=ok`

Пояснення результату:  
`realloc` повернув `NULL`, тобто перевиділення пам’яті не відбулося. При цьому попередній блок пам’яті не був втрачений: старий вказівник `ptr` залишився валідним, а дані в ньому збереглися. Тому при помилці `realloc` старий вказівник потрібно обов’язково звільнити через `free(ptr)`.

## Завдання 4.6

Отриманий результат запуску:
- `realloc(NULL, 5*sizeof(int)) -> 0x629ed2b0e2a0`
- `malloc(...) -> 0x629ed2b0e6d0`
- `realloc(b, 0) -> (nil)`

Пояснення:
- `realloc(NULL, size)` працює як `malloc(size)`, тобто виділяє нову пам’ять і повертає валідний вказівник.
- `realloc(ptr, 0)` у цьому запуску повернув `NULL`, що відповідає звільненню пам’яті, на яку вказував `ptr`.

Висновок:
Тестовий випадок підтвердив, що `realloc` з `NULL` виконує виділення пам’яті, а `realloc` з розміром `0` у нашому середовищі повертає `NULL` і фактично звільняє попередній блок.
