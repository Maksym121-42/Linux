## Завдання 1

Виклик `write(fd, buffer, nbytes)` може повернути значення, відмінне від `nbytes`.

У виконаному запуску отримано:
- `nbytes = 200000`
- `count = 65536`

Це означає, що `write()` виконав частковий запис: із запитаних 200000 байтів було записано лише 65536 байтів.  
Така поведінка можлива, коли дескриптор працює у неблокуючому режимі (`O_NONBLOCK`) і в системному буфері немає місця для всього обсягу даних.

Після кожного виклику `write()` потрібно перевіряти повернуте значення і, якщо записано менше байтів, виконувати дозапис у циклі.

## Завдання 2

Файл містить байти: `4, 5, 2, 2, 3, 3, 7, 9, 1, 5`.

Після виклику `lseek(fd, 3, SEEK_SET)` позиція у файлі встановлюється на зміщення `3` від початку файлу, тобто на 4-й байт.  
Далі виклик `read(fd, buffer, 4)` читає 4 байти, починаючи з цієї позиції.

У виконаному запуску отримано:
- `2 3 3 7`

Це і є вміст буфера після завершення `read`.

## Завдання 3

Для дослідження роботи `qsort` реалізовано автоматичний експеримент із різними типами вхідних масивів:
- випадковий;
- вже відсортований;
- зворотний;
- усі елементи однакові.

Для кожного типу масиву виконано кілька запусків сортування, після чого обчислено середню кількість порівнянь і середній час виконання.

Також реалізовано набір тестів правильності `qsort`:
- змішаний масив;
- вже відсортований масив;
- зворотний масив;
- масив з однакових значень.

Результати запуску:

- `ТЕСТ змішаний: УСПІХ`
- `ТЕСТ відсортований: УСПІХ`
- `ТЕСТ зворотний: УСПІХ`
- `ТЕСТ однакові: УСПІХ`

Результати експерименту:

- `випадковий: середні_порівняння=718231 середній_час=5.141 мс`
- `вже відсортований: середні_порівняння=382512 середній_час=1.288 мс`
- `зворотний: середні_порівняння=401952 середній_час=1.663 мс`
- `усі однакові: середні_порівняння=382512 середній_час=1.333 мс`

За отриманими даними найповільнішим виявився випадковий масив:
- `Найповільніший тип для цього qsort: випадковий`.

Проведені тести підтвердили правильність сортування, а експеримент показав, що продуктивність `qsort` залежить від структури вхідних даних.

## Завдання 4

Було виконано програму з викликом `fork()`:
- після `fork()` існує два процеси: батьківський і дочірній;
- обидва процеси виконують `printf("%d\n", pid);`.

Отриманий результат запуску:
- `67163`
- `0`

Це коректний результат успішного виклику `fork()`:
- у дочірньому процесі `fork()` повертає `0`;
- у батьківському процесі `fork()` повертає PID дочірнього процесу (додатне число, у цьому запуску `67163`).

Порядок виводу рядків не фіксований і залежить від планувальника процесів.

## Завдання 5

Реалізовано власну версію `qsort` (алгоритм швидкого сортування) і виконано порівняння з системною `qsort` на масиві об’єктів виду `(key, id)`.

Порівняння виконувалося тільки за полем `key`, тому для елементів з однаковим `key` порядок `id` не гарантується (нестабільне порівняння для перевірки стабільності сортування).

Результат запуску:

Початковий масив:  
`(3,0) (1,1) (3,2) (2,3) (1,4) (2,5) (3,6) (1,7) (2,8) (3,9) (1,10) (2,11)`

Системний `qsort`:  
`(1,1) (1,4) (1,7) (1,10) (2,3) (2,5) (2,8) (2,11) (3,0) (3,2) (3,6) (3,9)`

Власний `qsort`:  
`(1,4) (1,7) (1,10) (1,1) (2,11) (2,8) (2,3) (2,5) (3,2) (3,0) (3,6) (3,9)`

Кількість порушень порядку для елементів з однаковими ключами:
- системний `qsort`: `0`
- власний `qsort`: `9`

У цьому експерименті системний `qsort` зберіг порядок елементів з однаковим `key`, а власний `qsort` його порушив. Це показує різну поведінку сортувань на даних з рівними ключами.
