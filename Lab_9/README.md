## Завдання 1

Написано програму, яка отримує список облікових записів через `getent passwd`, визначає порогове значення `UID_MIN` з `/etc/login.defs` і перевіряє наявність користувачів з `UID >= UID_MIN`, крім поточного користувача.

Результат виконання:
- `UID_MIN = 1000`
- знайдений обліковий запис: `nobody (UID=65534)`

За формальною умовою `UID >= UID_MIN` у системі знайдено інший обліковий запис, окрім поточного користувача.

## Завдання 2

Написано програму, яка запускає команду `cat /etc/shadow` з підвищенням прав через `sudo`, хоча сама програма запускається від звичайного користувача.

Результат виконання:
- під час запуску запитано пароль користувача для `sudo`;
- після введення пароля виведено вміст файлу `/etc/shadow`.

Це підтверджує, що програма виконала команду від імені адміністратора за дозволеної в системі схеми доступу через `sudo`.

## Завдання 3

Програма створила початковий файл від імені звичайного користувача, після чого виконала копіювання через `sudo` у домашній каталог користувача.  
Далі програма перевірила дві дії від імені звичайного користувача: зміну файлу та видалення файлу.

Результат виконання:
- зміна файлу: `Permission denied`;
- видалення через `rm`: запит підтвердження для write-protected файлу, після підтвердження видалення виконано успішно.

Отримана поведінка означає:
- вміст root-власного файлу змінити не вдалося через відсутність прав запису у файл;
- видалення в домашньому каталозі вдалося, бо право на видалення визначається правами на каталог, а не лише правами на сам файл.


## Завдання 4

Програма по черзі виконала команди `whoami` та `id` для перевірки стану облікового запису користувача, від імені якого вона запущена.

Результат виконання:
- `whoami`: `pirat`
- `id`: `uid=1000(pirat) gid=1000(pirat) groups=1000(pirat),27(sudo),125(docker)`

Отримані дані показують:
- ім’я поточного користувача: `pirat`;
- основну групу користувача: `pirat` (`gid=1000`);
- додаткові групи: `sudo`, `docker`.

Таким чином, програма продемонструвала, що команда `id` виводить список груп, до яких належить користувач.

## Завдання 5

Програма створила тимчасовий файл від імені звичайного користувача та поетапно змінила власника і права доступу через `sudo chown` та `sudo chmod`.  
Після кожної зміни було перевірено можливість читання і запису від імені звичайного облікового запису.

Результат виконання:

- Початковий стан (файл створений користувачем):
  - читання: дозволено
  - запис: дозволено

- Після `chown root:root` і `chmod 600`:
  - читання: `Permission denied`
  - запис: `Permission denied`

- Після `chmod 666` (власник root):
  - читання: дозволено
  - запис: дозволено

- Після повернення власника користувачу і `chmod 600`:
  - читання: дозволено
  - запис: дозволено

Отримані результати показують, що можливість читання/запису визначається поєднанням власника файлу та бітів прав доступу.

У виводі видно різних власників (`pirat`, `root`) і різні права доступу (`rw-r--r--`, `rwxr-xr-x`, `rw-r-----` тощо).

Далі програма виконала спроби читання, запису і виконання для вибраних файлів.

Отримані результати показують, що доступ визначається власником файлу та бітами прав доступу, а спроби «обходу» без підвищення привілеїв не дають доступу до захищених файлів.

## Завдання 7
### Варіант 11
Досліджено різницю між виконанням `id` у shell та через системний виклик.

Варіанти запуску:
- `id` через shell: `system("id")`
- `id` через прямий системний виклик: `execve("/usr/bin/id", ...)` з поточним середовищем
- `id` через `execve` з порожнім середовищем

Результати:
- у всіх трьох випадках вивід однаковий:
  - `uid=1000(pirat) gid=1000(pirat) groups=1000(pirat),27(sudo),125(docker)`

Що це показує:
- `system("id")` запускає команду через shell (`/bin/sh -c`);
- `execve` запускає виконуваний файл напряму, без shell;
- у цьому експерименті значення `uid/gid/groups` не змінилися, бо вони визначаються обліковими даними процесу, а не способом запуску команди.
